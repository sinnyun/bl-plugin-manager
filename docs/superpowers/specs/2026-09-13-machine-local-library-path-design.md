# Blender 插件库管理器 2.0.0 全新架构设计

## 1. 决策

2.0.0 采用不兼容旧数据库的全新架构。项目仍处于开发阶段，不解析、不迁移、不合并旧版 `library.json` 中的任何字段。

首次连接一个含旧数据库的插件库时，管理器必须先把旧文件原样重命名为：

```text
<插件库>\.pm\archive\library.pre-2.0.<UTC时间戳>.json
```

归档文件设为只读，仅用于人工追溯。归档成功后创建全新的 schema 2 数据库；归档失败则停止初始化，绝不覆盖旧文件。

## 2. 目标

- 每台电脑独立保存插件库绝对路径，Blender 配置同步不会改变它。
- 别名、分类、标签、备注、收藏和自启等库配置随插件库一起同步。
- 启用状态、模块名、兼容性和错误等环境数据只保存在本机。
- 切换插件库只走一次受控激活流程，并正确读取目标库数据。
- 共享数据库损坏、版本不支持或发生并发修改时拒绝写入。
- 所有文件操作都被限制在插件库允许的目录中。
- 形成可测试、可拆分、可恢复的 2.0.0 基线。

## 3. 非目标

- 不保留 1.x 数据结构兼容层。
- 不恢复旧数据库中的分类、别名或运行记录。
- 不实现同步服务，也不自动合并同步工具生成的冲突副本。
- 不保证第三方插件本身兼容 Blender 5.2/Python 3.13。

## 4. 数据边界

### 4.1 共享数据库

位置固定为：

```text
<插件库>\.pm\library.json
```

最小结构：

```json
{
  "schema": 2,
  "library_id": "UUID",
  "revision": 0,
  "categories": [
    {"id": "uncategorized", "name": "未分类", "order": 0}
  ],
  "plugins": {}
}
```

单个插件记录只允许包含：

- 便携身份：`key`、`kind`、`rel`、`id`、`name`、`version`；
- 统一配置：`display_name`、`category_id`、`tags`、`note`、`favorite`、`startup`。

禁止写入共享数据库：绝对路径、设备名、模块名、是否启用、是否缺失、文件时间、本机扫描指纹、加载结果、异常堆栈、兼容性结论、Blender/Python 版本、挂载或仓库状态。

### 4.2 本机配置

Windows 默认位置：

```text
%LOCALAPPDATA%\BlenderPluginManager\machine.json
```

内容只包含 schema、设备 ID 和当前插件库路径：

```json
{
  "schema": 1,
  "device_id": "UUID",
  "library_path": "D:\\path\\to\\blender_addons"
}
```

`library_path` 在 Blender 插件偏好中标记为 `SKIP_SAVE`，只作为当前运行时界面值。

### 4.3 本机运行状态

位置：

```text
%LOCALAPPDATA%\BlenderPluginManager\state\<library_id>\<环境键>.json
```

环境键包含操作系统、Blender 主次版本和 Python 主次版本。这里保存 `module`、`enabled`、`missing`、扫描指纹、加载/恢复错误、残留状态和兼容性结果。官方仓库备份也保存在本机状态目录。

## 5. 生命周期

### 5.1 首次初始化

1. 校验所选目录真实存在且可读写。
2. 若 `.pm/library.json` 不存在，创建 `.pm` 和 schema 2 数据库。
3. 若文件是合法 schema 2，直接连接，不重新初始化。
4. 若文件是任何其它结构，先原样移动到 `archive`，设为只读，再创建 schema 2 数据库。
5. 任一步骤失败都回滚临时文件，并保持原数据库可恢复。

旧文件归档是安全保护，不是数据迁移；新数据库从插件目录重新发现插件，只产生便携身份和默认统一配置。

### 5.2 启动

顺序固定为：加载本机配置 → 验证路径 → 打开共享数据库 → 协调 Blender 挂载 → 刷新模块发现 → 扫描本机状态 → 应用自启 → 刷新界面。

本机路径不存在时保留配置但进入 `OFFLINE`，不得创建从其它电脑同步来的错误盘符目录。

### 5.3 切换插件库

所有入口统一调用 `LibraryService.activate(path)`：

1. 规范化并验证目录；
2. 丢弃目标路径的进程缓存，直接读取磁盘；
3. 必要时执行显式的新库初始化；
4. 保存本机路径；
5. 收敛管理器拥有的脚本目录和 `pmlib` 仓库；
6. 刷新模块后扫描一次；
7. 发布一次状态变更并重建界面。

属性回调不得自行扫描或保存数据库。

## 6. 数据一致性与故障处理

- 读取结果分为 `OK`、`MISSING`、`CORRUPT`、`UNSUPPORTED`、`CONFLICT`。
- `CORRUPT`、`UNSUPPORTED`、`CONFLICT` 均为只读故障状态。
- 保存前比较加载时签名、当前文件签名和 `revision`；变化时拒绝覆盖并提示刷新。
- 写入采用同目录临时文件、刷新缓冲区、`fsync`、原子替换和三代滚动备份。
- 缓存签名包含文件身份、创建/修改时间、大小和内容摘要；显式激活始终绕过缓存。
- 元数据修改使用字段级事务，调用者不能长期持有并覆盖完整可变快照。
- 同步工具产生的冲突文件只提示用户处理，不进行猜测性合并。

## 7. 文件安全

所有由数据库 `rel` 推导的路径统一经过 `resolve_record_path()`：

- 拒绝绝对路径、盘符路径、`..`、混合分隔符逃逸及符号链接/目录联接逃逸；
- 用 `realpath + commonpath` 保证结果位于 `<root>/addons` 或 `<root>/extensions`；
- 删除、更新、备份、打开目录和导入覆盖都必须使用同一解析器；
- ZIP 解压前限制成员数、单文件大小、总展开大小、压缩比、路径长度和 Windows 保留名称；
- 文件变更使用暂存、校验、交换、失败回滚事务。

## 8. Blender 集成

- `MountManager.reconcile()` 只管理本插件拥有的脚本目录名称前缀和固定 `pmlib` 仓库。
- 只保留一个指向当前真实目录的管理器挂载，清除失效的自有重复项，不触碰官方或用户条目。
- `ready` 必须同时检查配置条目和目标目录存在性。
- 注册过程记录每一步，失败后逆序回滚；注销可重复执行。
- 兼容性测试默认运行在独立后台 Blender 进程，本机会话模式需明确警告。
- 网络和纯文件 IO 放到工作线程，所有 `bpy` 调用留在主线程。
- UI 使用数据库和运行状态 revision 驱动更新，不再定时全量重建。

## 9. 模块边界

- `storage/shared_db.py`：schema 2、事务、冲突和原子写入；
- `storage/machine_config.py`：本机路径和设备 ID；
- `storage/local_state.py`：环境运行状态；
- `services/activation.py`：启动和切库编排；
- `services/mounts.py`：脚本目录与仓库协调；
- `services/plugin_files.py`：导入、更新、删除事务；
- `security/paths.py`、`security/archive.py`：路径和压缩包安全；
- `compatibility.py`：隔离兼容性检测；
- `tasks.py`：非阻塞任务控制；
- `operators/`：按激活、元数据、运行、文件、商店和诊断拆分。

## 10. 验收标准

- 两台模拟电脑使用不同绝对路径，共享同一库的别名、分类、备注、收藏和自启。
- 两台电脑的启用状态、错误和兼容性结果互不覆盖。
- 复制或同步整个库到另一绝对路径后，切换即可识别 schema 2 统一配置。
- 遇到旧数据库时完成只读归档并创建干净数据库；不会读取任何旧字段。
- 同步替换、并发保存、损坏 JSON 和未来 schema 都不会静默丢数据。
- 构造的越界记录无法读取、打开、更新或删除库外文件。
- 重复启停、安装失败、下载中断和文件交换失败均可恢复。
- 所有测试纳入 Git，并通过编译、单元、Blender 端到端、安全、性能、打包、安装回滚和 Blender 5.2.1 实机验证。

## 11. 发布与回滚

发布版本为 2.0.0。安装器先暂存并编译检查，再原子替换旧插件目录，同时保留上一安装版本。首次连接实际插件库前额外备份 Blender 偏好和挂载快照。

回滚插件代码不会自动恢复 schema 1 入口文件；如需人工回看，可从 `.pm/archive` 找到只读归档。2.0.0 初始化和实机安装必须分别记录日志，任何失败都不得删除归档。
