# Blender 插件库管理器架构审计与优化建议

## 1. 结论摘要

当前 1.0.3 的主要功能可以运行，源码能够编译，隔离环境中的 16 项回归检查和 161 项端到端检查均通过。但多电脑同步场景暴露出测试之外的系统性缺陷：本机路径、Blender 挂载配置、共享插件元数据和本机运行状态没有清晰分层。

最重要的结论是：不能只修 `library_path`。必须同时处理本机路径、陈旧挂载、共享数据库缓存、数据库写入冲突、运行状态隔离和危险文件路径，否则其它电脑仍可能出现“路径正确但数据不对”“界面显示已挂载但目录不存在”或“某台电脑把另一台的状态写回共享库”。

项目处于开发阶段，用户已确认不考虑旧数据兼容。因此不再分 1.0.4/1.1.0 修补，而是发布一次干净的 **2.0.0 架构重建**：旧数据库仅做只读归档，新建 schema 2 数据库；从第一版就完成本机/共享数据分层、冲突保护、文件边界、服务拆分、非阻塞任务与可追踪测试。这样可以避免为已知错误的数据模型继续增加迁移层和临时兼容代码。

## 2. 审计范围与证据

本次检查覆盖：

- `bl_plugin_manager` 下全部 15 个 Python 模块；
- Blender 5.2.1 LTS 实机中的插件、脚本目录、扩展仓库和偏好状态；
- 当前同步插件库的 `.pm/library.json`；
- 安装、打包、导入、更新、启停、兼容性测试和异常恢复流程；
- 现有隔离回归及端到端测试；
- 临时目录内的故障注入，不改动真实插件库。

当前验证基线：

- Python 源码编译：通过；
- 回归测试：16/16 通过；
- 端到端测试：161/161 通过；
- Blender MCP 协议与插件连接：正常；
- 插件安装版本：1.0.3；
- 当前源码与 Blender 5.2 安装目录中的 `.py` 文件一致。

## 4. 缺陷清单

### P0-01：本机库路径保存在同步偏好中

**状态：已实机确认。**

`library_path` 是普通 `AddonPreferences.StringProperty`，随 `userpref.blend` 保存。多电脑同步会把另一台电脑的盘符带到本机。配置目录中已经出现多个 `userpref_*_Conflict.blend`，与故障现象一致。

**运行表现：** 插件能启用，但扫描、列表、启停、更新和自动挂载指向不存在目录。

**优化：** 路径保存到 `%LOCALAPPDATA%\BlenderPluginManager\machine.json`；Blender 属性只作运行时/UI 值，不随漫游偏好持久化。

### P0-02：Blender 挂载配置同样被跨电脑同步

**状态：已实机确认。**

脚本目录和扩展仓库也存于 `userpref.blend`。代码只按当前绝对路径查找脚本目录，换电脑后会新增条目而不是收敛已有的管理器条目，最终形成 `名称`、`名称.001` 等重复项。`pmlib` 仓库会被重新指向当前路径，但旧脚本目录不会自动清理。

**运行表现：** 同名插件被多路径发现、模块解析指向旧位置、扩展仓库失效、状态面板误报正常。

**优化：** 建立 `MountManager.reconcile()`：按管理器拥有的名称前缀和仓库模块识别自身条目，保留一个当前有效条目，清理仅属于本插件且已失效的旧条目；绝不删除用户或系统仓库。

### P0-03：共享数据和本机运行状态混在同一记录

**状态：已由真实数据库确认。**

以下字段应该跨电脑共享：

- `display_name`、`category`、`tags`、`note`、`favorite`、`startup`；
- 插件的便携身份和声明元数据，例如 `key`、`rel`、`id`、`name`、`version`。

以下字段依赖电脑、Blender 版本、Python 版本或仓库模块，不应作为全局共享真相：

- `module`、`enabled`、`missing`；
- `load_state`、`load_error`、`last_error`、`restore_error`、`residue`；
- `compat`、`compat_detail`；
- 绝对 `origin_path`；
- 带本机文件时间的 `metadata_fingerprint`。

当前这些字段全部写入共享 `library.json`。一台电脑运行 Blender 5.2/Python 3.13 的测试结果，会覆盖另一台不同版本环境看到的状态。

**优化：** 共享库保留用户配置和便携元数据；本机运行状态进入 `%LOCALAPPDATA%\BlenderPluginManager\state\<library_id>\<blender-version>.json`。共享数据库新增稳定 `library_id`，用于关联本机状态。

### P0-04：同步替换可能命中旧数据库缓存

**状态：代码路径确认。**

缓存签名只有 `st_mtime_ns + st_size`。同步工具可能保留修改时间，内容也可能恰好等长；插件随后返回旧缓存。切库操作又会扫描并保存这个旧对象，存在把新同步数据覆盖回去的风险。

**优化：** 缓存签名加入 `st_dev`、`st_ino`、`st_ctime_ns`；显式切库必须清除缓存并使用 `use_cache=False` 读取。UI 读取改为数据库修订号驱动。

### P0-05：数据库相对路径可逃逸插件库并删除外部目录

**状态：故障注入已确认。**

`remove_plugin()`、`replace_from_zip()` 和“打开文件夹”等流程直接使用：

```python
os.path.join(root, rec["rel"])
```

没有验证最终路径仍位于 `root/addons` 或 `root/extensions`。临时测试把 `rel` 设置为 `../outside_plugin` 后，调用永久删除流程成功删除了插件库之外的受控测试目录。

**运行表现：** 损坏、冲突或被修改的共享数据库可能让删除/更新操作作用于库外文件。

**优化：** 所有记录路径统一经过 `resolve_record_path()`，使用 `realpath + commonpath` 验证容器边界、记录类型和目录名；失败时只报错，不执行任何文件写操作。

### P0-06：数据库损坏后会静默建立新数据库并覆盖入口文件

**状态：故障注入已确认。**

JSON 解析失败时会复制 `.corrupt`，随后把内存设为空数据库。正常扫描会继续运行并保存，把原 `library.json` 替换为只有扫描结果的新文件。虽然 `.corrupt` 尚在，但用户界面看起来像分类、别名突然丢失。

**优化：** 数据库加载返回明确状态 `OK/MISSING/CORRUPT/UNSUPPORTED`。`CORRUPT` 时进入只读故障状态，禁止扫描保存；提供“查看备份/显式恢复”入口。保留多代滚动备份。

### P0-07：数据库没有并发和同步冲突保护

**状态：代码路径确认。**

每个操作符读取完整 JSON、修改少数字段，再原子替换完整文件。原子替换只能防半写文件，不能防“读取后文件被另一台电脑更新”。后保存者会覆盖先同步到达的新数据。

**优化：** `LibraryDB` 保存时比较加载基线签名和当前磁盘签名；不一致则抛出可见的 `DatabaseConflictError`，刷新后重试字段级事务。共享写入统一通过 `update_record_fields()`、`update_categories()` 等事务接口，禁止调用方长期持有可变完整快照。

### P0-08：切库流程重复扫描和保存

**状态：代码路径确认。**

目录选择操作符先创建数据库对象，再赋值 `prefs.library_path`。赋值回调会用另一个对象扫描，操作符随后又用原对象扫描。这增加旧对象覆盖同步数据的概率，也造成重复 IO。

**优化：** `LibraryService.activate(path)` 串行完成验证、无缓存加载、本机路径保存、挂载协调、一次扫描和一次 UI 刷新。属性回调只处理直接手工编辑，不参与受控激活流程。

### P0-09：启动时先扫描、后注册扩展仓库

**状态：代码路径确认。**

`_bootstrap_prefs()` 在仓库未挂载时先执行 `sync_library()`。扩展模块名依赖实际仓库模块；找不到当前仓库时 `_active_repo_module()` 默认返回 `blender_org`。随后代码才创建 `pmlib`，数据库里可能已经写入错误模块名。

**运行表现：** 扩展显示存在，但启停时报模块不存在，或者测试结果绑定到错误模块。

**优化：** 启动顺序改为“恢复本机路径 → 协调挂载 → 刷新模块发现 → 扫描数据库 → 应用自启”。

### P0-10：测试没有纳入版本控制

**状态：已确认。**

`.gitignore` 排除了 `_test/`、`_mcp_test/` 和 `_migrate/`。当前仓库只跟踪 24 个文件，没有任何测试文件。45 个操作符中约 17 个被现有测试直接调用，在线商店、更新全部、导入操作符、诊断、分类重命名/删除等关键入口缺少直接覆盖。

**优化：** 把可重复测试移入 `tests/blender/` 并纳入 Git；一次性审计脚本和历史数据继续忽略。建立失败退出码、故障注入、安全边界和安装包测试。

### P1-01：插件自身注册/热重载生命周期不可靠

**状态：代码风险确认。**

`__init__.py` 在 `import bpy` 之后判断 `"bpy" in locals()`，因此首次导入也总会热重载子模块；这不是 Blender 常用的“仅二次加载”判断。注册过程中若某个类失败，已经注册的类没有事务回滚，容易留下管理器自己的半注册状态。

**优化：** 修正热重载哨兵；注册所有类时记录成功集合，异常立即逆序注销；重复启停加入生命周期测试。

### P1-02：强制清理插件残留的归属判断过于宽松

**状态：代码风险确认。**

`_force_unregister_classes()` 按 `__module__` 前缀遍历并注销 Blender 类型，还包含特定插件硬编码。若模块名解析错误或多个插件共享命名空间，可能注销非目标类。

**优化：** 测试前后拍摄精确类型快照，只清理由本次加载新增且可确认归属的类；无法确认时提示重启，不强制猜测。

### P1-03：“一键测试兼容性”会在当前生产会话执行第三方代码

**状态：设计风险确认。**

测试逐个真实启停第三方插件。插件的 `register()` 可以修改场景、文件、偏好、网络或全局处理器，Blender Undo 无法完整恢复。失败插件还可能导致崩溃。所有 `_PMBase` 操作符统一声明 `UNDO`，但文件和偏好操作实际上不可撤销。

**优化：** 默认在独立后台 Blender 子进程测试；当前会话模式改为高级选项并明确警告。移除文件/偏好类操作符的 `UNDO` 标记。

### P1-04：ZIP 缺少资源限制和明确安全策略

**状态：部分动态验证。**

标准库 `zipfile.extractall()` 对测试中的简单 `../` 路径进行了归一化，未逃逸临时目录；因此未确认传统 ZIP Slip。但代码没有限制文件数量、单文件大小、总解压大小、压缩比、路径长度或 Windows 保留名称，仍可能被压缩炸弹拖死 Blender 主线程。

**优化：** 解压前逐条验证成员并设定上限；只提取识别出的单一插件根；拒绝绝对路径、驱动器路径、异常压缩比和超限包。

### P1-05：网络和大部分长任务阻塞 Blender 主线程

**状态：代码确认。**

商店下载使用最长 40 秒的同步 `urlopen()`；仓库同步、批量更新、全库扫描和兼容测试也在操作符 `execute()` 中同步完成。代码没有 modal timer、后台线程队列或取消机制。

**运行表现：** 网络不通或大库更新时 Blender 界面长时间无响应，用户可能误判为崩溃并强制结束，增加数据库/插件替换中断风险。

**优化：** 下载和纯文件 IO 放入工作线程，Blender API 操作回到主线程；使用 modal 任务、进度、取消和超时。每个任务明确可恢复边界。

### P1-06：UI 每 0.3 秒全量重建列表

**状态：代码确认。**

`maybe_rebuild()` 只有在 0.3 秒内才跳过；超过后即使过滤条件和数据库都没变化，也会清空并重新创建全部 `CollectionProperty` 项。面板绘制还会多次新建 `LibraryDB` 并深拷贝整个数据库。

**运行表现：** 152 个插件时产生持续 CPU、内存分配和界面抖动；网络盘上更明显。

**优化：** 用“当前库 ID + 数据库 revision + 过滤签名 + Blender 运行状态 revision”决定刷新；只有事件变化才重建。一次绘制周期共享只读快照。

### P1-07：安装脚本不是事务式安装

**状态：代码确认。**

`install.ps1` 先递归删除旧插件，再复制新插件；复制失败会留下没有可用版本的状态，也没有自动备份。Blender 正运行时替换文件不会让内存模块自动更新。

**优化：** 复制到同目录 staging，验证版本和编译后交换；保留 `.previous` 回滚；检测运行中的 Blender 并明确要求停用/重启；安装后验证每个目标版本。

### P1-08：错误被吞掉，成功提示不完全可信

**状态：代码确认。**

桥接、刷新、保存偏好和初始化中存在大量宽泛 `except Exception: pass`。例如 `save_prefs()` 失败不会反馈给调用者，操作符仍可能报告成功。

**优化：** 建立结构化诊断结果和日志等级；关键状态变更失败必须传播到 UI；仅允许已证明可忽略的刷新兼容异常降级，并记录原因。

### P1-09：官方仓库备份错误地放在共享库

**状态：代码确认。**

`official_repo_backup.json` 位于共享 `.pm`，但官方仓库目录和偏好属于具体电脑。另一台电脑可能读取并恢复不属于自己的仓库路径。

**优化：** 官方仓库快照改存到本机状态目录，并按 Blender 版本保存；共享数据库不保存 Blender 偏好快照。

### P2-01：模块边界过大

`operators.py` 约 67 KB、45 个操作符、83 个函数/方法；`library.py` 同时负责路径、导入、备份、扫描、事务替换和更新。UI、存储、Blender API 和文件系统副作用交织，导致测试必须启动完整 Blender。

**优化：** 逐步拆为 `services/activation.py`、`services/plugin_files.py`、`storage/shared_db.py`、`storage/local_state.py`、`blender/mounts.py`、`blender/addon_runtime.py`、`security/archive.py` 和按功能分组的 operators。拆分必须在行为测试建立后进行，不能一次性重写。

## 5. 真实托管插件错误概览

当前共享数据库记录了约 20 个加载失败插件。它们不是插件库管理器自身的错误，但管理器需要正确隔离和呈现这些环境相关结果：

| 类型 | 典型表现 |
|---|---|
| 缺少旧模块 | `No module named 'bgl'`、`No module named 'audioop'` |
| Python ABI 不匹配 | Python 3.11 编译内容无法在 Python 3.13 使用、`bad magic number` |
| Blender API 变化 | 旧菜单、旧偏好面板或类型已删除 |
| 类注册残留 | `register_class(...): already registered` |
| 循环导入/符号缺失 | `partially initialized module`、`cannot import name` |
| 插件自身定义错误 | 未定义类、无效键位映射等 |

这些结果必须按 `Blender版本 + Python版本 + 仓库模块 + 操作系统` 隔离。否则一台电脑的失败会让其它电脑错误显示为不兼容。

## 6. 推荐目标架构

### 6.1 数据分层

```text
共享插件库/
├── addons/
├── extensions/
├── inbox/
├── trash/
└── .pm/
    ├── library.json          # schema 2：别名、分类、备注、收藏、自启、便携元数据
    ├── backups/              # schema 2 的滚动写入备份
    └── archive/              # 只读的 2.0 以前数据库，不参与运行

%LOCALAPPDATA%/BlenderPluginManager/
├── machine.json              # 本机：active_library_path、设备标识
└── state/<library_id>/
    ├── blender-5.2.json       # 本机运行状态和加载测试
    └── repository-backup.json
```

共享 `library.json` 使用稳定 `library_id` 和递增 `revision`。插件记录中仅保留可跨电脑解释的字段。本机状态按环境键保存 `module`、`enabled`、错误、残留和兼容测试结果。

### 6.2 服务边界

- `SharedMetadataRepository`：共享 JSON 的 schema 2 校验、初始化、备份、冲突检测和字段级事务；不包含旧结构迁移器。
- `LocalStateRepository`：本机路径、挂载快照、当前 Blender 运行状态。
- `MountManager`：把本机期望路径协调成唯一有效脚本目录/扩展仓库。
- `LibraryService`：激活、刷新、导入、删除、更新的业务顺序；UI 不直接拼装文件操作。
- `PluginRuntime`：模块解析、启停、精确残留检测和环境指纹。
- `ArchivePolicy`：安全检查、限额解压和插件根识别。
- `TaskController`：长任务进度、取消、后台 IO 与主线程 Blender API 调度。

### 6.3 故障状态

库应明确区分：

- `UNCONFIGURED`：本机尚未选择路径；
- `OFFLINE`：已配置路径暂时不可用；
- `METADATA_MISSING`：库结构存在但没有数据库；
- `METADATA_CORRUPT`：数据库损坏，只读保护；
- `CONFLICT`：数据库在本次编辑期间被同步替换；
- `MOUNT_DEGRADED`：脚本目录或仓库未正确挂载；
- `READY`：路径、数据库和挂载均真实有效。

UI 不应把“偏好中存在条目”显示成“正常”。

## 7. 全新数据库初始化策略

用户已明确放弃旧数据兼容和恢复。2.0.0 不读取旧数据库字段，也不生成分类恢复差异。

首次连接库时：

1. 若不存在数据库，直接创建 schema 2；
2. 若存在合法 schema 2，正常连接；
3. 若存在任何其它数据库，先原样移动到 `.pm/archive/library.pre-2.0.<UTC时间戳>.json` 并设为只读；
4. 只有归档成功后才创建全新 schema 2 数据库；
5. 归档或创建失败时停止，不覆盖原文件。

安装前仍备份 `userpref.blend`、当前脚本目录和扩展仓库快照，用于回滚 Blender 集成设置。这些备份不用于恢复旧插件库元数据。

## 8. 验收标准

- 每台电脑可以使用不同绝对路径，并稳定读取同一套别名、分类、备注、收藏和自启设置。
- 非 schema 2 数据库只读归档后创建新库，旧字段从未进入新数据库。
- 同步替换数据库后不会命中旧缓存或静默覆盖新数据。
- 损坏数据库不会被自动重建覆盖。
- 任意 `rel` 值都不能让读写、更新或删除越出插件库容器。
- Blender 偏好中最多存在一个属于管理器的当前脚本目录和一个正确仓库。
- 状态面板会把不存在目录显示为离线/失效。
- 兼容性测试结果不会跨 Blender/Python 环境污染。
- 所有测试纳入版本控制，并覆盖安全、同步、挂载、注册、安装和主要操作符。
- 安装过程可回滚，重启/重载后版本和路径恢复可验证。
