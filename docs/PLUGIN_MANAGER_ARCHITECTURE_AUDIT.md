# 插件库管理器架构审计与优化结果

## 结论

本轮已将插件从“把绝对路径和运行状态混入 Blender/共享配置”的旧结构，改为“总插件数据库 + 本机身份 + 按设备配置 + 本机运行状态”四层结构。插件只接管扩展仓库、库内插件启用状态和自定义脚本目录。停用时不再读取工厂启动文件、覆盖 `userpref.blend` 或保存全部 Blender 偏好。

2.2.0 起，跨电脑共享的插件资料改由独立的总插件数据库 `.pm/catalog.json` 保存，并以稳定
`plugin_id`（而非库内路径）为键；本机安装位置改为 `plugin_id → 相对路径` 绑定。这样各电脑
安装的插件数量与目录名不同时，仍能按插件身份自动连线，别名与分类不会因目录改名而丢失，
也不会因同一目录换插件而错误继承。自启标记从共享数据调整为本机数据——各电脑安装的插件
不同，自启属于本机行为，不应互相覆盖。详见
`docs/superpowers/specs/2026-09-18-master-catalog-design.md`。

2.1.0 起，兼容性实测改为不阻塞界面的分步任务，低频维护入口集中在插件偏好设置，3D 视图顶部栏入口移除。

## 已修复的高风险缺陷

| 缺陷 | 结果 |
|---|---|
| 多电脑同步覆盖不同盘符 | 库路径移入本机 `machine.json`，Blender 属性使用 `SKIP_SAVE` |
| 设备身份随保存变化 | 首次生成 UUID，后续路径/名称修改保持不变 |
| 别名、分类无法随库迁移 | 便携资料保存在 `<库>/.pm/catalog.json`（总插件数据库） |
| 目录名不同的同一插件连不上别名 | 记录以稳定 `plugin_id` 为键，按 manifest id / 声明名 / 目录名自动匹配 |
| 同一目录换插件后错误继承别名 | 声明名冲突时不采用目录名线索，新建条目；旧条目保留可重连 |
| 启用状态在不同电脑互相覆盖 | 每台设备使用 `<库>/.pm/devices/<device-id>.json` |
| 自启标记在不同电脑互相覆盖 | 自启属于本机行为，保存在本机状态，不进总插件数据库 |
| 缺失插件被从启用清单删除 | 同步只更新本机实际扫描到的键，未知键保留 |
| 安装/加载管理器就擅自接管 | `management_enabled` 明确持久化；停止状态不会隐式恢复 |
| 停用时影响全部 Blender 设置 | 只重置扩展仓库、自定义脚本目录、库内插件启用状态 |
| 工厂重置或全局偏好保存破坏设置 | 源码禁止调用四个危险操作，静态测试持续检查 |
| 自动开启联网访问 | 改为只读取状态并提示用户，绝不赋值 |
| 按名称猜测并删除“孤儿挂载” | 旧启停与猜测清理入口已删除 |
| 官方仓库恢复点跨电脑污染 | 不再创建官方仓库偏好快照，停止时按受管字段恢复默认 |
| 数据库缓存命中同步旧文件 | 签名包含设备、inode、ctime、mtime、大小 |
| 数据库相对路径逃逸库外 | 读写/更新/删除统一验证容器边界 |
| 损坏数据库被空数据覆盖 | 损坏状态只读，拒绝保存 |
| 同步文件混入本机字段导致整库只读 | 读取时丢弃未知/本机字段，写入时直接拒绝 |
| 安装中断留下半个版本 | 临时目录编译后交换，并保留上一版本用于回滚 |

## 目标数据架构

```text
共享插件库
├── addons/、extensions/、inbox/、trash/
└── .pm/
    ├── catalog.json             总插件数据库：插件身份与共享资料，schema 1
    ├── devices/<uuid>.json      每设备启用意图、仓库、脚本目录
    ├── backups/
    └── archive/                 旧版 library.json 只读归档

本机 LOCALAPPDATA
├── machine.json                 UUID、设备名、库路径、接管状态
└── state/<library-id>/<env>.json
                                 plugin_id → 相对路径绑定，以及模块名、
                                 是否启用、自启标记、兼容性与错误
```

共享主数据库以稳定 `plugin_id` 为键，不允许出现绝对路径、模块名、启用状态或自启。设备配置位于共享库中是有意设计：它需要随库同步，但每个设备只写自己的文件。设备身份与本机绑定位于本机，不能交给同步软件同步。

## 接管状态机

### INACTIVE

- 管理器可以显示路径，但不修改原生配置。
- Blender 启动或管理器重新加载不会自动接管。
- 原生配置不存在“按名称清理”的副作用。

### ACTIVATING / ACTIVE

1. 初始化并扫描 schema 2 库。
2. 新设备从当前原生仓库、脚本目录和库内插件状态建立自己的配置。
3. 已知设备应用自己的配置。
4. 强制保持库根脚本目录和库扩展目录两个必需绑定。
5. 每两秒比较受管字段；只有变化时才原子写入设备文件。
6. 原生面板新增的自定义仓库、脚本目录和库内插件启停进入当前设备配置。

### DEACTIVATING / ERROR

停止前先同步，之后停用库内插件、清空自定义脚本目录、移除自定义仓库并恢复官方仓库默认字段。Blender 内置仓库和管理器本身保留。单项失败会进入 `ERROR` 并返回明细，不报告虚假成功。

## 精确安全边界

允许写入：

- 当前插件库目录及其 `.pm` 数据；
- `%LOCALAPPDATA%/BlenderPluginManager`；
- 当前 Blender 进程内的扩展仓库集合、自定义脚本目录集合和库内插件启用集合。

明确禁止：

- `bpy.ops.wm.save_userpref()`；
- `read_factory_settings`、`read_homefile`、`read_userpref`；
- 写入或替换任何真实 `userpref.blend`；
- 修改联网权限、主题、快捷键、语言、界面、系统、渲染、资产库或启动文件；
- 未验证路径上的递归删除或移动；
- 根据显示名称推测条目归属。

## 同步策略

- 总插件数据库、设备配置与本机状态均使用 UTF-8 JSON、临时文件、刷新和原子替换。
- 总插件数据库以稳定 `plugin_id` 为键，本机安装位置保存在本机绑定中，因此各电脑可用不同目录名与盘符。
- 设备文件按 UUID 分片，避免三台电脑同时保存各自启用清单时覆盖同一文件。
- 修改设备名称只更新名称，UUID 不变。
- 运行状态与自启标记以 `library_id + 环境指纹` 隔离在本机，不会把一台电脑的模块路径、启用状态、自启标记或加载失败写给另一台。
- 同步工具发生同一设备文件冲突时保留显式冲突文件；插件不会吞掉损坏 JSON 后重建覆盖。

## 测试与证据

- 普通 Python 单元测试覆盖设备身份、设备配置、状态机、总插件数据库的字段归属与损坏保护、跨电脑身份匹配（目录改名 / 声明名冲突 / 类型区分 / 同机第二副本 / 旧数据迁移）、路径边界、危险 API 静态约束，以及不计 Blender 的兼容性任务逻辑（目标筛选、单步推进、取消后置生效、启用态复测的停用/恢复）；2.2.0 最终结果为 77 项通过，1 项按运行条件跳过。
- Blender 回归测试（Blender 5.2.1 LTS，隔离运行）：31/31 通过。覆盖受管范围恢复、官方仓库默认字段、在线权限哨兵、挂载状态缓存、总插件数据库本机模块解析与 `rel`/`module` 排除，以及模态调度、`retest_all` 保留未重测旧结果、顶部栏未注册与工具面板移除。
- Blender 端到端测试（Blender 5.2.1 LTS，隔离运行）：186/186 通过。覆盖初始化、导入、扫描、启停、分类、别名、更新、迁移、停止/重启/显式恢复、非活动零修改，以及兼容性任务的完整 `start → tick → 收尾` 链路（逐项处理、计时器注销、`load_state` 逐条落盘、目标恢复原未启用状态）。
- UI 冒烟测试（Blender 5.2.1 LTS）：用模拟布局真实执行各面板与列表行 `draw`，无错误；断言偏好设置含维护/迁移入口、侧栏不再有迁移面板、任务运行时显示取消入口。
- 2.2.0 实测中发现并修复的三个真实缺陷：扫描路径误把目录名当插件声明名；`import_plugin_dir` 在补齐用户字段后回写旧引用，导致 `note` 等字段丢失（`KeyError: 'note'`）；多个 `LibraryDB` 句柄先后保存同一文件时被并发保护误判为冲突。三者均已由单元与端到端用例覆盖。
- 两套 Blender 启动器都设置独立配置、脚本、TEMP、本机配置和本地状态目录，并在 Python 入口验证解析后的真实路径。运行前后真实 Blender 5.2 `userpref.blend` 未被改动（mtime 保持运行前的时间戳）。
- 2.2.0 安装包：`dist/bl_plugin_manager-2.2.0.zip`（30 个发行文件，不含缓存或编译产物），SHA-256 为 `7DD081DB3E5AD6D0CAFB3302E492B3222B911ED1EC116BF29ACCB057A7279B34`。



### 2.2.0 总插件数据库与跨电脑匹配

2.1 及以前以库内相对路径为共享数据库的键，导致两个多电脑问题：同一插件在不同电脑目录名
不同则连不上别名与分类；同一路径换插件则新插件错误继承旧别名。2.2.0 引入独立的总插件数据
库 `.pm/catalog.json`（`bl_plugin_manager/storage/catalog.py`），要点：

- 记录以稳定 `plugin_id` 为键，扫描时按 manifest id / 插件声明名 / 目录名匹配
  （`bl_plugin_manager/services/catalog_sync.py`），并累积历史名称与目录名，改名后仍能连回。
- 两条防误连规则：扩展与传统插件互不匹配；资料库与本机插件都声明了名称且不同时，不采用
  目录名线索，改为新建条目（旧条目保留，重装后自动连回）。
- 本机安装位置改为 `plugin_id → 相对路径` 绑定，保存在本机状态；各电脑可用不同目录名与盘符。
- 自启标记由共享数据调整为本机数据：各电脑安装的插件不同，自启不应互相覆盖。
- 总插件数据库写入侧拒绝本机字段，读取侧丢弃未知字段，避免一个多余字段让整库只读。
- 移除插件只解除本机绑定；总资料库条目与其它电脑不受影响，重装后自动连回。
- 旧 `library.json` 首次连接时自动迁移（保留别名、分类、标签、备注、收藏；自启转入本机
  状态），旧文件归档为只读。旧库损坏时进入只读，绝不覆盖。
- 本机派生字段（`module`、`enabled`、`startup`、`missing`、`rel` 等）继续只写入本机状态，
  总插件数据库只保存可跨电脑解释的资料。

### 2.0.1 模块解析修复

共享扫描曾在合并便携字段后提前返回，导致新库没有把当前电脑解析出的 `module` 写入本机状态文件。插件记录因此可能存在，但单独启用时报“无法解析插件模块名”。2.0.1 在同一次扫描中为传统插件和扩展插件解析真实模块名，并通过 `LibraryDB.save()` 将 `module`、`enabled` 和 `missing` 仅写入环境本地状态；共享数据库继续排除这些字段。该约束在 2.2.0 中继续成立，并由 `tests/test_catalog_view_v1.py` 与回归用例验证（总插件数据库中不出现 `module` 与 `rel`）。

### 2.1.0 兼容性测试任务与界面入口

「一键测试插件支持」原先在一次 `execute()` 内遍历全部插件，期间 Blender 界面不重绘也不响应输入，且没有可见进度。2.1.0 改为 `bpy.app.timers` 驱动的分步任务：

- 新增 `bl_plugin_manager/compat_task.py`，容纳目标筛选、任务状态机、单步执行与摘要文案。该模块不 import `bpy`，所有 Blender 副作用通过注入的 `api`（`set_enabled` / `is_module_enabled` / `module_residue`）完成，因此可在普通 Python 进程完整测试。
- 每个计时器事件只处理一个目标，事件之间把控制权交还 Blender。单插件加载本身仍是同步阻塞，取消不会中断它。
- 范围可选「继续未完成项」（默认，仅测无本轮结果的项目）或「全部重新测试」。重测时只在目标**被实测到**才覆盖其 `load_state`，因此中途取消不会销毁尚未重测的旧结果。
- 取消只设置请求：当前目标处理结束后停止后续任务，已完成结果写入数据库、报告与界面；取消后的摘要区分已完成与未完成数量，且不报告为错误。
- 无论完成、取消或异常，收尾都移除计时器、清空状态栏、保存记录、刷新列表并生成可查看摘要；停用插件时同样安全收尾。
- 侧栏显示 `已完成 / 总数`、当前插件名与进度条，状态栏同步显示进度；任务运行时入口变为「取消」。

界面信息架构在 2.1.0 收敛为两个入口：

- **3D 视图侧边栏**保留高频插件管理：库连接状态、搜索筛选、插件列表与详情、批量操作、导入、在线商店、更新、扫描报告，以及兼容性测试入口与运行时进度。
- **编辑 → 偏好设置 → 插件 → 插件库管理器**收纳低频配置与维护：设备名称、库路径、启用/修复与卸载挂载、刷新、诊断、启动同步策略、迁移收编、清理失败插件残留、清除更新标记、官方商店目录关联。
- 侧栏「迁移与启动控制」子面板（`PM_PT_tools`）删除；库级菜单不再承载诊断、清除更新与卸载挂载。
- 3D 视图顶部栏模块（`header.py`，含 `plugin_manager.header_popup`）删除，不再注册任何 `VIEW3D_HT_header` 回调。

操作符与数据存储未变，仅移动入口，因此旧流程与自动化调用仍兼容。启动同步策略 `sync_startup_on_launch` / `startup_disable_unmarked` 此前只声明、无入口也无调用；2.1.0 把入口放入设置面板，并在 Blender 启动就绪后按标记同步一次（默认只启用，不主动停用）。

## 仍需遵守的运行约束

- 兼容性实测会执行第三方插件的 `register()`，第三方代码自身仍可能报错或产生副作用；应只测试可信插件。
- 兼容性实测已改为可取消的分步任务，界面在测试期间保持可交互；但**单个插件的加载或卸载仍是同步阻塞**，取消只在当前插件处理结束后生效，无法中断它。若插件自身在 `register()` 中卡死，界面会在该项上停顿。
- 网络下载和部分大库扫描仍可能占用 Blender 主线程。当前通过超时、状态提示和原子写入降低风险，但后续版本可继续拆成可取消后台任务（不使用后台线程调用 Blender API）。
- Blender 新版本若改变官方仓库字段，应先在隔离环境更新适配测试，再扩大支持版本；不能通过加载真实用户配置来探测默认值。

## 交付验收

- 不同设备路径、名称和启用清单互不覆盖。
- 共享别名、分类、备注与库一起迁移。
- 管理器停止后原生三项范围恢复默认，其它偏好哨兵不变。
- 重新加载保持停止；显式启用后恢复当前设备清单。
- 原生面板更改可同步，必需库绑定不会被永久删掉。
- 缺失或加载失败插件保留启用意图。
- 隔离单元、回归和端到端测试全部通过后才生成安装包。
